# 웹과 크롤링, 처음부터

- 19장 초보자 강의용 대본
- 화면에는 짧은 문구만 두고, 아래 내용은 발표자가 말한다.
- 예상 시간: 설명 45~55분, 실습 10~15분
- 법률 부분은 일반적인 교육 설명이다. 개별 사건의 법률 자문이 아니다.

## 01. 웹과 크롤링, 처음부터

화면 문구: `웹과 크롤링, 처음부터`

오늘은 파이썬 코드부터 시작하지 않겠습니다. 코드부터 보면 한 사이트에서 한 번 된 다음, 다른 사이트에서 왜 안 되는지 설명을 못 합니다. 빈 페이지가 오고, 로딩만 돌고, 로그인 화면만 뜨고, 에이전트는 읽었다고 하는데 정작 값은 틀리고. 이런 일이 계속 생깁니다.

그래서 오늘은 웹이 정보를 주는 방식부터 보겠습니다. 클라이언트, 서버, DB. 이 세 개를 잡고 HTML과 API가 어디에 붙는지 본 다음, 그제야 크롤링으로 넘어갑니다. 마지막에는 제가 실제로 쓰는 Chrome 확장 프로그램으로 이어가겠습니다.

강의 중간에 용어가 많이 나와도 겁먹을 필요 없습니다. 오늘 나오는 용어는 거의 전부 `클라이언트 → 서버 → DB` 그림을 조금씩 확대해서 보는 겁니다.

## 02. 클라이언트 → 서버 → DB

화면 문구: `클라이언트 → 서버 → DB`

웹은 일단 세 덩어리만 보면 됩니다. 요청하는 쪽이 클라이언트, 요청을 받는 쪽이 서버, 서비스가 기억해야 할 걸 넣어두는 곳이 DB입니다. 거칠게 말하면 셋 다 컴퓨터입니다.

클라이언트가 “이거 줘”라고 요청합니다. 서버는 요청을 받고 필요한 데이터를 찾습니다. 그 데이터가 DB에 있으면 꺼내서 답을 만들어 클라이언트에 돌려줍니다. 이게 전부입니다.

실제로는 서버가 여러 대일 수도 있고 DB 대신 파일이나 검색엔진을 쓸 수도 있습니다. 그런데 처음부터 그 예외를 다 외우면 그림이 안 잡힙니다. 오늘은 이 세 덩어리로 시작하겠습니다.

## 03. 클라이언트는 사람이 아니다

화면 문구: `클라이언트는 사람이 아니다`

클라이언트는 사람 그 자체가 아닙니다. 사람이 쓰는 Chrome, 스마트폰 앱, 차량 화면, 냉장고 같은 프로그램과 기기가 클라이언트입니다. 인터넷을 통해 무언가를 달라고 요청하는 쪽이면 됩니다.

사람은 Chrome 주소창에 글자를 입력합니다. 그다음부터 요청을 보내고, 답을 받고, 화면을 그리는 일은 Chrome이 합니다. 앱도 똑같습니다. 앱이 서버에 주문 목록을 달라고 하고, 서버가 답을 주면 앱이 화면으로 보여줍니다.

그러니까 “내가 웹사이트에 들어갔다”를 컴퓨터 말로 바꾸면 “내 클라이언트가 서버에 요청을 보냈다”에 가깝습니다.

## 04. google.com → DNS → IP

화면 문구: `google.com → DNS → IP`

우리가 `google.com`을 치는 것도 요청의 시작입니다. 그런데 컴퓨터끼리는 보통 이런 이름보다 IP 주소로 상대를 찾습니다. DNS는 `google.com`이라는 이름에 연결된 IP를 찾아주는 전화번호부 같은 겁니다.

여기서 하나만 고치겠습니다. DNS가 보통 `IP:포트`까지 통째로 바꾸는 건 아닙니다. 일반적인 웹 브라우징에서 DNS의 핵심은 이름을 IP로 찾는 일입니다. 포트는 프로토콜과 URL, 서버 설정이 정합니다. HTTPS의 기본 포트는 보통 443이라 주소창에서 안 보일 뿐입니다.

터미널에서 `dig +short google.com`을 치면 IP가 여러 개 나올 수 있습니다. 서버가 한 대뿐이라는 뜻도 아니고, 지역과 시점에 따라 답이 달라질 수도 있습니다.

실습: `dig +short google.com`

## 05. 서버는 남의 컴퓨터다

화면 문구: `서버는 남의 컴퓨터다`

IP를 따라가면 결국 프로그램이 실행 중인 다른 컴퓨터가 나옵니다. 그 컴퓨터가 요청을 기다리고 있으면 서버라고 부릅니다. 데이터센터에 있을 수도 있고 클라우드 안에 있을 수도 있습니다.

내 맥북도 서버가 될 수 있습니다. 터미널에서 간단한 서버를 켜고 `localhost`로 들어오면, 제 맥북이 “이라샤이마세” 하고 답을 돌려줍니다. 서버는 특별한 쇳덩어리 이름이 아니라 역할 이름입니다.

서버는 요청을 받으면 약속해 둔 일을 합니다. DB를 읽을 수도 있고, 파일을 줄 수도 있고, 계산만 해서 결과를 돌려줄 수도 있습니다.

실습: `python3 -m http.server 4318`

## 06. DB는 서비스의 기억이다

화면 문구: `DB는 서비스의 기억이다`

DB는 초보자 기준으로 아주 튼튼한 엑셀이라고 생각하면 됩니다. 회원, 상품, 주문, 게시글, 가격, 재고 같은 서비스의 기억이 들어갑니다. 여러 프로그램이 동시에 읽고 써도 망가지지 않게 만든 저장 시스템이라고 보면 됩니다.

많은 사이트에서는 이 데이터가 존재 이유입니다. 쇼핑몰에서 상품과 재고가 없고, 커뮤니티에서 회원과 글이 없으면 화면 껍데기만 남습니다. 그래서 제가 “셋 중 DB가 제일 중요하다”고 말했던 겁니다.

다만 모든 DB가 별도 컴퓨터는 아니고, 서버가 항상 SQL을 쓰는 것도 아닙니다. 오늘은 엑셀 비유로 시작하고, 나중에 관계형 DB와 NoSQL을 따로 배우면 됩니다.

## 07. DB → 서버 → HTML

화면 문구: `DB → 서버 → HTML`

자, 서버가 DB에서 상품 이름과 가격과 재고를 꺼냈습니다. 이걸 사람이 보기 좋게 HTML로 조립해서 Chrome에 줄 수 있습니다. Chrome은 HTML과 CSS와 이미지를 받아 화면으로 그립니다.

우리가 보는 웹 화면은 DB 자체가 아닙니다. 서버가 만든 답을 Chrome이 그린 결과입니다. 그래서 화면의 글자를 바꿨다고 DB까지 바뀌는 게 아닙니다.

요즘은 서버가 완성 HTML을 주지 않고, 빈 껍데기와 JavaScript만 준 다음 데이터를 나중에 불러오는 경우도 많습니다. 그건 11장에서 다시 보겠습니다.

## 08. 바꿔도 서버는 그대로

화면 문구: `바꿔도 서버는 그대로`

HTML은 쉽게 말해 내 브라우저가 받은 전단지입니다. F12를 열고 Elements에서 서울 날씨를 27도에서 99도로 바꿀 수 있습니다. 화면은 진짜로 바뀝니다.

그렇다고 날씨 서버를 해킹한 건 아닙니다. DB도 그대로입니다. 새로고침하면 서버가 준 원래 값으로 돌아옵니다. 내 손에 들어온 복사본만 바꾼 겁니다.

이 구분이 중요합니다. 크롤러도 대개 서버 응답이나 브라우저 안의 DOM을 읽습니다. 화면을 읽었다고 서버 내부 DB에 직접 들어간 건 아닙니다.

실습: 본인이 관리하는 테스트 페이지에서만 Elements의 텍스트를 바꾼다.

## 09. 사람은 HTML, 프로그램은 API

화면 문구: `사람은 HTML, 프로그램은 API`

HTML은 사람이 보기 좋습니다. API는 프로그램이 쓰기 좋게 데이터를 주고받는 창구입니다. 화면 꾸밈보다 이름, 가격, 재고 같은 값을 JSON으로 또박또박 주는 쪽에 가깝습니다.

API가 DB를 통째로 여는 건 아닙니다. 서버가 허용한 데이터와 기능만, 정해 둔 권한과 횟수로 줍니다. 카카오 지도 API나 공공데이터 API처럼 공식 창구가 있으면 그걸 먼저 쓰는 편이 안정적입니다.

API 말고도 공식 다운로드, RSS, Atom, sitemap, webhook, 이메일 알림이 있을 수 있습니다. 원하는 데이터가 있다고 무조건 HTML부터 긁지 말고, 공식 창구가 있는지 먼저 봅니다.

## 10. curl로 받고, selector로 고른다

화면 문구: `curl로 받고, selector로 고른다`

공식 창구가 없고 공개 페이지에서 필요한 값을 읽어야 할 때 HTML을 가져옵니다. 터미널의 `curl`은 브라우저 화면 없이 HTTP 요청을 보내고 응답을 보여줍니다.

그 안에서 `.price`, `#stock`, `article h1`처럼 원하는 부분을 지정하는 것이 selector입니다. 정확히는 `curl`이 selector로 잘라주는 게 아닙니다. `curl`은 응답을 받고, BeautifulSoup이나 Cheerio나 브라우저 코드가 selector로 값을 꺼냅니다.

실습에서는 `curl`로 HTML을 본 다음, 개발자도구에서 가격 요소를 눌러 `.price`가 어느 부분인지 보여주면 됩니다. 초보자는 selector 문법 전체보다 “페이지에서 원하는 위치의 주소”라고 먼저 이해하면 됩니다.

## 11. 빈 HTML, 나중에 오는 데이터

화면 문구: `빈 HTML, 나중에 오는 데이터`

요즘 웹은 처음부터 완성 HTML을 주지 않는 경우가 많습니다. 빈 `<div id="app"></div>`만 주고, JavaScript가 API를 다시 호출해 데이터를 받아 화면을 채웁니다. 이걸 CSR이라고 부릅니다.

그래서 `curl`에서는 텅 비었는데 Chrome에서는 상품과 가격이 보일 수 있습니다. Chrome은 JavaScript를 실행했고, 쿠키와 토큰을 붙여 Fetch나 XHR 요청을 더 보냈기 때문입니다.

이때 개발자도구 Network 탭에서 JSON 응답이 보일 수 있습니다. 그렇다고 숨은 API가 보이는 순간 접근 권한과 이용 조건이 사라지는 건 아닙니다. 공개되고 허용된 범위에서만 씁니다.

## 12. Bright Data 승소, 무제한 허가는 아님

화면 문구: `Bright Data 승소, 무제한 허가는 아님`

자, 원문에는 “크롤링은 실제로 범죄”라고 세게 적었는데 강의에서는 그렇게 말하지 않겠습니다. 크롤링이라는 기술 자체가 곧 범죄는 아닙니다. 검색엔진도 크롤링하고, 회사 내부 테스트도 크롤링합니다.

사례로 Meta와 Bright Data가 붙은 사건을 보겠습니다. 2024년 1월 23일 미국 캘리포니아 북부연방법원은 Meta의 일부 약식판결 신청을 기각하고, Meta의 계약위반 청구에 관해 Bright Data의 약식판결 신청을 받아들였습니다. 이 쟁점에서는 Bright Data가 이겼습니다.

법원은 당시 기록에서 Bright Data가 로그인 상태로 비공개 데이터를 긁었다는 증거가 없다고 봤고, 당시 약관도 로그아웃 상태의 공개 데이터 수집까지 금지하지 못한다고 판단했습니다.

하지만 “공개 웹은 뭐든, 얼마든지, 어떤 목적으로든 긁어도 된다”는 판결은 아닙니다. 약관, 접근권한, 저작권, DB권, 개인정보, 기술적 보호조치, 요청량, 이용 목적은 따로 봐야 합니다. 공개 화면과 무제한 이용권은 같은 말이 아닙니다.

근거: [법원 명령문 PDF](https://www.courthousenews.com/wp-content/uploads/2024/01/meta-platforms-v-bright-data-ruling-motion-for-summary-judgment.pdf)

## 13. 사이트는 왜 막을까

화면 문구: `사이트는 왜 막을까`

사이트가 막는 첫 이유는 데이터가 돈이기 때문입니다. 상품, 가격, 재고, 리뷰, 매물을 모으고 갱신하는 데 비용이 듭니다. 경쟁사가 결과만 통째로 가져가면 운영자는 당연히 싫어합니다.

다른 이유는 서버 비용과 안정성입니다. 사람은 페이지를 보고 잠깐 쉬지만, 잘못 만든 봇은 같은 URL을 초당 수십 번 부르고 실패할수록 더 세게 재시도합니다. DB와 이미지 서버까지 같이 느려질 수 있습니다.

그렇다고 요청이 많으면 바로 DDoS라고 부르면 안 됩니다. 실제 장애와 의도, 규모를 따져야 합니다. 운영자는 IP 하나만 보는 게 아니라 계정, 요청 순서, 속도, 헤더, 세션, 실패 패턴을 같이 봅니다.

공개 프로필도 대량으로 모아 결합하면 개인정보 문제가 커질 수 있습니다. “화면에 보인다”와 “사람 수백만 명의 정보를 모아도 된다”는 다른 문제입니다.

## 14. 막으면, 다른 흔적을 본다

화면 문구: `IP → 지문 → 행동 → 로그인 → CAPTCHA`

처음에는 같은 IP에서 너무 많이 들어오면 그 IP를 막았습니다. 수집자가 IP를 바꾸자 운영자는 국가와 통신사, 데이터센터 대역, 브라우저 지문, 쿠키와 계정, 클릭 순서까지 같이 보기 시작했습니다.

IP를 사거나 실제 기기를 많이 쓰는 쪽도 있습니다. 화면의 휴대폰 농장은 그 구조를 설명하려고 만든 재연 이미지입니다. 규모가 커질수록 IP만 필요한 게 아니라 기기, 세션, 계정, 운영 인프라까지 필요해집니다.

운영자는 로그인과 휴대폰 인증, 속도 제한, CAPTCHA, JavaScript 챌린지, 동적 토큰, 가짜 링크나 honeypot, 캔버스와 이미지 렌더링 같은 방어를 겹칩니다. `visibilityState`와 포커스, 실제 사용자 입력이 있었는지도 볼 수 있습니다.

근데 로그인과 CAPTCHA를 세게 걸면 봇만 줄어드는 게 아닙니다. 사람도 귀찮아서 떠나고 MAU가 줄 수 있습니다. 그래서 운영자는 막는 강도와 사용성을 계속 저울질합니다. AI가 퍼즐을 풀기 시작하자 사이트도 퍼즐 하나만 믿지 않고 브라우저와 행동 신호를 함께 보기 시작했습니다.

여기서 선을 하나 긋겠습니다. 방어가 어떻게 생겼는지 설명하는 것과, 남의 접근 제한을 실제로 무력화하는 방법을 가르치는 건 다릅니다. 강의에서는 허용된 공개 데이터와 자기 계정, 자기 사이트 실습만 다룹니다.

## 15. requests → BeautifulSoup → Selenium

화면 문구: `한 번 만드는 것보다 유지가 어렵다`

예전에 파이썬을 배운 분들은 `requests`로 HTML을 받고 BeautifulSoup으로 자르는 방식부터 시작했을 겁니다. JavaScript가 필요해지면 Selenium으로 브라우저를 띄워 클릭했습니다.

진짜 어려운 건 처음 한 번 성공시키는 일이 아니었습니다. 사이트가 리뉴얼되고 클래스 이름이 바뀌고, 로그인 순서가 달라지고, 쿠키 배너가 하나 생길 때마다 코드가 깨졌습니다.

그래서 크롤링 운영이 노가다가 됐습니다. 새 기능을 만드는 게 아니라 상대 사이트 양식을 계속 쫓아갑니다. selector 하나 고치고, 로딩 시간을 늘리고, 다시 실패 로그를 보는 일의 반복입니다.

지금도 이 문제는 없어지지 않았습니다. AI가 selector를 찾아줄 수는 있지만, 사이트가 바뀌면 검증하고 고치는 일은 남습니다.

## 16. 내 Chrome ≠ 에이전트 브라우저

화면 문구: `내 Chrome ≠ 에이전트 브라우저`

Claude나 Codex가 웹에 대해 대답한다고 해서 지금 그 페이지를 실제로 읽었다는 뜻은 아닙니다. 예전에 학습한 내용일 수도 있고, 검색 결과의 짧은 문구만 봤을 수도 있습니다. 실시간 값이면 출처와 시간을 다시 확인해야 합니다.

URL을 실제로 열어도 방식이 다릅니다. 어떤 도구는 `curl` 같은 HTTP 요청만 보내고, 어떤 도구는 새 headless 브라우저를 띄웁니다. 새 브라우저에는 내 쿠키, 로그인, 방문 기록, 확장 프로그램이 없습니다.

“Chrome 엔진을 쓴다”와 “내가 지금 쓰는 Chrome 프로필을 쓴다”도 다릅니다. 후자는 로그인 세션이 이어져 덜 막힐 수 있지만, 그만큼 개인정보와 계정 권한을 에이전트에 넘기는 문제가 생깁니다.

## 17. 200 OK도 실패할 수 있다

화면 문구: `200 OK도 실패할 수 있다`

상태코드가 200이어도 성공이 아닐 수 있습니다. 내용이 CAPTCHA, 로그인 페이지, “잠시만 기다리세요” 화면일 수 있습니다. 그래서 성공 여부는 원하는 값이 실제로 나왔는지로 확인해야 합니다.

초보자는 실패 이유를 네 가지로 먼저 나누면 됩니다. 첫째, JavaScript를 안 돌려서 빈 HTML만 왔습니다. 둘째, 내 로그인 정보와 쿠키가 없는 새 브라우저입니다. 셋째, 광고와 분석 요청이 계속 돌아서 로딩이 끝나지 않습니다. 넷째, 탭이 뒤에 열려 사이트가 포커스가 없다고 판단했습니다.

Amazon 같은 페이지에서는 “네트워크가 완전히 조용해질 때까지” 기다리면 끝이 안 날 수 있습니다. 페이지 전체가 멈추기를 기다리지 말고, 필요한 값이 나타났는지를 기준으로 멈춰야 합니다.

개발자용으로 더 들어가면 이전 페이지 정보인 referrer, 동의 팝업, 무한 스크롤, Shadow DOM, canvas, 지역과 A/B 테스트도 원인이 됩니다. 지금은 용어를 외우기보다 “내가 보는 화면과 에이전트가 받은 화면이 다를 수 있다”만 잡으면 됩니다.

백그라운드 탭에서는 사이트가 `document.visibilityState`나 `document.hasFocus()`로 포커스를 확인할 수 있고, 브라우저 자체도 숨은 탭의 타이머를 줄입니다.

근거: [MDN Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)

## 18. 도구마다 맡는 일이 다르다

화면 문구: `API → Reader → Browser → Managed`

도구는 네 칸으로만 보겠습니다. `공식 자료 → 읽기 변환 → 실제 브라우저 → 전문 서비스`입니다. 처음부터 가장 비싼 도구를 쓰는 게 아니라, 막힌 이유에 맞춰 한 칸씩 올라갑니다.

먼저 공식 API, export, RSS, sitemap을 봅니다. 공개 페이지를 읽기 좋은 Markdown으로 바꾸는 게 목적이면 Jina Reader 같은 도구가 맞습니다. 단순 HTTP로 안 되면 JavaScript를 실행하는 브라우저가 필요합니다.

`insane-search`가 잘되는 이유도 한 방에 모든 벽을 뚫어서가 아닙니다. 공개 API와 피드 같은 가벼운 길부터 찾고, 안 되면 실제 브라우저까지 단계적으로 올립니다. 브라우저가 받은 공개 데이터를 찾아 결과가 맞는지도 확인합니다. 로그인이나 유료 장벽에서는 멈춘다고 README에 경계를 적어뒀습니다. 이건 프로젝트 README가 설명하는 방식이지, 독립 기관이 성공률을 검증했다는 뜻은 아닙니다.

Aside는 제품 설명상 아예 브라우저 자체가 에이전트의 작업장입니다. 기존 웹사이트와 계정을 브라우저 안에서 직접 쓰는 구조라, 별도 fetch 도구보다 실제 탭과 세션을 이어가기 쉽습니다.

규모와 지역, 로그인 상태 운영이 필요하면 Bright Data나 Oxylabs 같은 전문 서비스를 빌립니다. 여러 IP와 브라우저, 실패 재시도 같은 운영을 대신 묶어주는 겁니다. 돈을 내면 운영이 쉬워지는 거지, 남의 데이터에 대한 권리까지 사는 건 아닙니다.

내가 쓰는 실제 Chrome을 조작하는 방법도 있습니다. 오늘 마지막에 볼 Chrome 확장 프로그램이 가장 쉬운 예입니다. 내 브라우저와 허용된 계정에서만 쓰고, 민감한 탭과 로그인 정보는 따로 보호해야 합니다.

진행자 참고: 개발자 방식에는 Playwright, Chrome DevTools Protocol(CDP), CUA, AppleScript, bookmarklet이 있습니다. Chrome 원격 디버깅 예시 포트는 보통 `9222`이고 `9292`가 아닙니다. 초보자에게는 실습 뒤 질문이 나올 때만 설명합니다.

- [Jina Reader](https://r.jina.ai/docs)
- [Aside](https://aside.com/)
- [Bright Data Browser API](https://docs.brightdata.com/scraping-automation/scraping-browser/introduction)
- [Oxylabs Web Unblocker](https://developers.oxylabs.io/advanced-proxy-solutions/web-unblocker)

## 19. 한 번 고르고, 바뀔 때만 알림

화면 문구: `한 번 고르고, 바뀔 때만 알림`

제가 쓰는 방법은 Web Change Alert로 관심 있는 값 하나를 직접 고르는 겁니다. 가격, 재고, 버튼 문구처럼 필요한 부분을 한 번 선택하고 주기를 정합니다. 값이 달라졌을 때만 Chrome 알림을 받습니다.

장점은 실제로 쓰는 Chrome 안에서 돌아간다는 점입니다. JavaScript가 실행되고 로그인 세션도 이어질 수 있어서 단순 서버 크롤러보다 덜 막히는 경우가 있습니다. AI가 매번 페이지 전체를 읽지 않으니 토큰도 거의 들지 않습니다.

다만 만능은 아닙니다. 현재 공개 코드의 자동 검사는 탭을 `active: false`로 열기 때문에, 포커스와 visibility를 확인하는 사이트에서는 실패할 수 있습니다. 로그인 만료, selector 변경, CAPTCHA, 너무 짧은 확인 주기도 따로 봐야 합니다.

다음 실습에서는 세 가지만 먼저 잡겠습니다. 안정적인 selector를 고르는 법, 사이트에 부담을 주지 않는 확인 주기, 그리고 “200이 왔다”가 아니라 “원하는 값이 실제로 맞다”를 검증하는 법입니다.

제품과 코드:

- [GitHub](https://github.com/minwoo19930301/web-change-alert)

## 발표자용 짧은 마무리

웹은 클라이언트가 서버에 요청하고, 서버가 DB나 다른 저장소에서 값을 찾아 답을 주는 구조입니다. HTML은 사람용 화면 재료고 API는 프로그램용 창구입니다. 공식 창구가 없을 때 HTML이나 렌더링 결과에서 값을 꺼내는 것이 크롤링입니다.

크롤링은 한 번 성공시키는 것보다 계속 맞게 가져오는 일이 어렵습니다. 그래서 가장 단순하고 허용된 방법부터 시작하고, 실패 원인을 확인하면서 도구를 올려야 합니다. 마지막에는 원하는 값 하나만 골라 바뀔 때 알림을 받는 식으로 문제를 작게 만드는 게 좋습니다.
